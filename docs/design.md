# 1. 定位与边界

本文设计一个「全局记忆」插件：一份跨会话生效、由用户手动增删的长期事实与偏好清单，在每次对话中自动进入模型上下文。

## 1.1 与「要求台账」的分工

两者都能让模型看到用户的要求，但归属和来源根本不同，混在一起会让两条链路互相污染：

| 维度 | 要求台账（已有） | 全局记忆（本文） |
| --- | --- | --- |
| 作用域 | 单个会话 | 所有会话 |
| 内容来源 | 从会话日志自动抽取 | 用户手动写入 |
| 真相位置 | 会话日志（可重建） | 独立存储（唯一来源） |
| 生命周期 | 会话结束即止 | 长期存在，直到用户删除 |
| 失效方式 | 被新要求取代 / 被改写 | 只能显式删除 |

关键结论：**二者的状态来源不能合并**。台账是日志的纯函数投影，随时可以从事件重建；全局记忆没有所属会话，日志里根本不存在它，因此它必须是插件持有的持久化数据。把它们塞进同一个投影单元会得到一个既不能重建、也不该按会话销毁的怪物。

## 1.2 非目标

- 不做自动抽取。用户说得清楚「要手动增删」，自动抽取会立刻引入「模型以为你在说偏好」的误判，而这类误判的影响面是全局的——一次误判污染所有后续会话。
- 不做语义检索或向量召回。全局记忆的规模由预算而非检索能力决定，一个总长几百 token 的清单直接全量注入更可靠。
- 不跨机器同步。本地存储，用户需要时自己复制文件。
- 不替代 `AGENTS.md`。宿主自带的 `dsh-agent-instructions` 是 workspace 级、按目录发现、支持嵌套的；本插件是宿主独立的一份全局清单。两者可以并存，职责不同，见 2.6。
- 不参与工具拦截。全局记忆是「模型应该知道的事」，不是「必须被阻止的事」；拦截留给要求台账的 `ban`。

## 1.3 设计目标

1. **唯一来源**：清单内容只存在于一处，不与会话日志、profile 配置形成第二份真相。
2. **每步可见**：通过运行时上下文注入每一个会话的每一次请求，不依赖模型检索。
3. **成本可控且诚实**：全局记忆会乘以所有会话的请求数，必须有硬预算；超出时不回答并提示调整，而不是静默截断。
4. **编辑安全**：写入必须原子、可校验；一次坏的编辑不能把清单变成空白。
5. **可迁移**：纯文本可导出、可导入，用户能备份和手工修复。

# 2. 方案设计

## 2.1 数据模型

```ts
interface MemoryStore {
  version: number          // 存储格式版本，用于未来迁移
  revision: number         // 每次写入 +1，供前端做乐观并发
  entries: MemoryEntry[]
}

interface MemoryEntry {
  id: string               // 稳定 id，创建时生成
  text: string             // 一条事实/偏好，纯文本，不解释 Markdown
  title?: string           // 可选短标题，用于列表展示
  tags: string[]           // 自由标签，仅用于分组与筛选，不参与注入逻辑
  enabled: boolean         // 停用但保留，避免「删了又想加回来」
  createdAt: number
  updatedAt: number
}
```

两个刻意的选择：

- **`enabled` 而不是删除**。用户想临时关掉一条（比如某个项目的约定当前不用），停用比删除更常用。真正删除仍然提供。
- **不存 Markdown/富文本**。注入到上下文里的每一条最终都是一行文本，允许富文本只会让「编辑后的样子」和「模型看到的样子」产生偏差。

## 2.2 存储

用宿主已有的领域存储（`ctx.storageDomain.open(spec)`），而不是插件自己写 JSON 文件。理由是它已经提供了本设计要的三件事，自己实现只会更差：

- **zod 校验**：每次加载都校验记录，坏记录不会变成运行时异常。
- **原子写入**：`KvTable.put` / `delete` 由后端保证，不会出现写一半的文件。
- **版本迁移**：`DomainSpec.version` + `compatibleVersions`，未来加字段有正规路径。

```ts
const spec = {
  name: 'global-memory',
  version: 1,
  layout: 'single',                 // 整份清单一个文档，便于整体导出
  global: { schema: storeSchema, initial: emptyStore() },
  tables: {},
}
```

整份清单放 `global` 而非按条分表，是因为它需要作为一个整体被版本化和原子替换；单条并发编辑由 `revision` 乐观锁覆盖。

插件启动时 `open()`，把返回的 `Domain` 句柄保存在插件上下文里，并用 `ctx.effect` 注册 `close()`。

## 2.3 注入

沿用与要求台账相同的通道，`ctx.systemPrompt.context()`：

```ts
ctx.systemPrompt.context({
  name: 'global-memory',
  order: 155,            // 紧跟在 directive-ledger(150) 之后
  required: true,
  text: () => render(currentStore()),
})
```

三个必须坚持的约束：

1. **字节稳定**。内容不变时渲染结果必须逐字节相同，否则每一步都会写一条新的运行时上下文快照，既膨胀日志又摧毁前缀缓存。渲染不包含时间戳、不依赖 Map 迭代顺序，按 `id` 排序。
2. **预算显式**。超过 `budgetTokens` 时不发起本次请求，并提示用户手动调整（见 2.5.2）——绝不让模型看到一份被悄悄裁剪过的清单。
3. **空则零可见**。清单为空时不注入任何文本，避免每次请求都带一个空标题。

渲染形态（示意）：

```
用户的全局偏好（所有会话通用）：
- 回答一律用中文
- 不要用 npm，统一 pnpm
- 提交前跑 node --test
```

## 2.4 编辑界面

主入口是设置页：`settings.section` 注册一个「记忆」分页，与宿主其它设置页并列。

页面能力：

- 列表：按标签分组，显示启用状态、最后修改时间
- 新增 / 编辑 / 删除 / 启停
- 单条与总量的占用提示（字符数 + 估算 token），让人看见成本
- 导入 / 导出（纯文本或 JSON）

数据通路用插件自己的 HTTP 路由（`ctx.webServer.register`），与既有插件的做法一致；读取走 `GET /plugins/global-memory/state`，写入走 `POST`。所有路由必须过 `ctx.connection.requestRejection(req)` 这道信任栅栏——这一点在要求台账的删除接口上已经踩过一次：不带认证直接请求会拿到 401。

不上 `capabilities` 之外的自动化：没有 `/memory` 命令也能用，但提供一个 `/memory add <文本>` 会让「边聊边记」顺手很多，作为可选功能放在 P1。

## 2.5 容量与质量

「全局记忆变长会不会拉低输出质量」不能只用条数回答。真正伤害质量的是**内容类型**，其次是**总量**；两层要分开治理。

### 2.5.1 收什么、不收什么

全局记忆是**短陈述句的集合**，不是文档仓库。判断标准是「这条是否需要模型每次都照着做」：

| 适合收 | 不适合收 | 该去哪 |
| --- | --- | --- |
| 工具与环境的既定选择（我用 pnpm，不装全局包） | 部署步骤、多阶段流程 | skill 或 `AGENTS.md` |
| 恒常的沟通偏好（一律中文、结论写在最前） | 某个项目的代码规范全文 | 该项目的 `AGENTS.md` |
| 稳定的个人事实（在 Windows 上工作、只读环境） | 一次性的任务背景 | 直接写在对话里 |
| 明确的长期禁忌（不要动 `D:\prod`） | 与当前任务耦合的中间结论 | 要求台账（会话级） |

不合适的条目不是「先收着以后再说」——它们会持续占用每一次请求的注意力预算，且与其它条目争夺注意力，比单纯的 token 开销更贵。

### 2.5.2 单一硬上限与提示

本设计**只用一个上限**：`budgetTokens`（默认 400）。注入文本超过它时，插件不截断、不压缩，而是**这一次不回答**，同时给出调整建议，由用户手动改。原设计的三道闸门（单条长度、总条数、注入预算）已废弃，理由见 2.5.3。

超限时的行为：

1. **不发起请求**。在 `agent/request` 瀑布里拦下，模型这一次不被调用；不是先答一半再报错。
2. **给出一条用户能照着做的提示**：当前占用多少、上限多少、超出多少、该去哪个页面改。
3. **不做任何自动修复**。不截断、不删除、不停用——改什么、删哪条由用户决定。

为什么选择「不回答」而不是「截断后照常回答」：截断会让用户以为记忆已经全部生效，实际有一部分模型从没看到。在长对话里这种偏差极难发现，而它导致的正是「我明明记过，为什么你不照做」——本插件要消除的那类困惑。不回答是可感知的、可立即纠正的。

### 2.5.3 为什么从三道闸门收敛成一个

原设计要求单条长度、总条数、注入预算三道限制。放弃它们的原因是：三道限制意味着三种不同的失败方式，而用户只需要知道一件事——**现在能不能用，以及不能用时该改哪里**。

- 单条过长、总条数过多，本质是「别把记忆当文档写」的提醒，属于建议而非阻断条件。降级为设置页的占用提示即可。
- 注入预算才真正决定模型看到多少，也是唯一直接影响输出质量的因素。只保留它，语义清晰：**超了就是不能用**。
- 单一上限让「为什么不能用」只有一个答案，无需解释三种阈值之间的关系。

### 2.5.4 为什么不做自动压缩

一个自然的想法是：既然有上限，超限时让插件把清单压短不就好了。本设计**不采用静默压缩**，理由在「超限即不回答」的设定下更充分——压缩会让「超限」消失于无形，而本设计恰恰要让它显形。

**首要理由：压缩丢的正是信息量最大的部分。** 全局记忆里每条都是祈使句，摘要倾向于省掉限定词——工具名、路径、版本、条件。而这些恰恰是唯一无法从上下文推导出来的部分：

| 原文 | 压缩后 | 结果 |
| --- | --- | --- |
| 提交前跑 `node --test` | 提交前跑测试 | 跑什么测试？不可执行 |
| 不要用 npm，统一 pnpm | 统一包管理器 | 用哪个？等于没说 |
| 不要动 `D:\prod` | 不要动生产目录 | 哪个目录？无法判界 |

**第二：静默压缩破坏可核对性。** 「不回答」的代价是明确的，用户能确认「我写的那条还在不在」。摘要的损失看不见，用户无法核对，这与「用户手动管理」的定位冲突。

**第三：不确定输出破坏字节稳定。** 注入文本必须对未变化的内容逐字节一致，否则每一步都要写一条新的运行时上下文快照，既膨胀日志又摧毁前缀缓存。模型生成的摘要每次措辞都可能不同，即使语义等价也会触发整块重写。

可选的辅助手段，都不改变「由人来改」这一点：

1. **确定性去重**（默认开启，无模型成本）。规范化后完全相同的条目只渲染一条，纯字符串比较，可逆、无损失。真正普遍的冗余是重复，不是冗长。
2. **占用提示**（默认开启）。设置页显示当前 token 占用与上限的差距，接近上限时标出可疑重复，由人判断是否合并。

还要说明一点：压缩是在用有损手段解决一个**分流问题**。清单变长的常见原因不是「记得太多」，而是把该放进 skill 或 `AGENTS.md` 的长内容记进了全局记忆。正确做法是 2.5.1 的分流，而不是事后压缩。

## 2.6 与要求台账的优先级

这是本设计最需要显式回答的问题：两份清单都进入系统提示，说法冲突时听谁的。

规则：

1. **会话内的台账优先**。用户在某个会话里刚说「这次用英文」，不能因为全局记忆里写着「一律中文」而被覆盖。
2. **冲突不自动消解，只并列呈现**。注入文本里用「全局偏好」和「本会话要求」两个独立段落分别渲染，让模型看到的是事实，而不是插件替它做的裁决。
3. **不做跨插件写入**。全局记忆不读取、不修改要求台账，反之亦然；两个插件各自只负责自己的数据。

选择第 2 条而非「自动比较取其一」，是因为误判的代价不对称：并列呈现最坏只是多费几行 token，错误消解会让用户刚下的指令静默失效——那正是这套插件要解决的问题本身。

## 2.7 与宿主的 `AGENTS.md` 加载器的关系

宿主自带 `dsh-agent-instructions`，从 `AGENTS.md` / `CLAUDE.md` 加载 workspace 级指令，支持按目录嵌套发现。当前该能力是 **inactive**。

两者的分工应当是：

- `AGENTS.md`：**项目**的属性。跟着仓库走，可以提交、可以 review、可以因目录不同而不同。
- 全局记忆：**人的**属性。跟着用户走，跨项目恒常，不进入任何仓库。

因此本插件不读 `AGENTS.md`，也不写它。若用户希望某条约定跟着项目走，正确的做法是写进仓库的 `AGENTS.md`；若希望它跟着自己走，就放进全局记忆。这一点应当写进插件说明，否则用户会困惑「我该记在哪」。

## 2.8 风险与失效模式

- **污染面放大**：一条错误的记忆影响所有会话。缓解：`enabled` 默认开启但一键可停；编辑页显示「此条会出现在你所有的对话中」。
- **超限后无法继续对话**：这是「超限即不回答」的固有代价。缓解：提示里写清该去设置页改什么；设置页不经过模型调用，永远可用；`/memory` 命令同样绕开模型，保证不用离开对话也能自救。见 2.5.2。
- **与台账打架**：见 2.6，用并列呈现而非自动裁决。
- **写入损坏**：并发编辑互相覆盖。缓解：`revision` 乐观锁，版本不匹配时拒绝并要求刷新。
- **存储后端缺失**：`storageDomain` 未挂载时插件无法工作。缓解：把它列为硬依赖，插件不激活而不是降级成静默无操作。

## 2.9 配置项

```yaml
- id: global-memory
  name: '@local/dsh-global-memory'
  config:
    budgetTokens: 400        # 唯一硬上限；超出则不回答并提示调整
    textLanguage: auto       # auto | zh | en
    allowAgentWrite: false   # 是否允许模型写入全局记忆，默认关闭
```

`allowAgentWrite` 默认 `false` 是刻意的：全局作用域下，让模型自主写入意味着一次误判会污染所有后续对话，而用户无法事先审查。开启后也只提供「建议写入、等待确认」而非直接落盘。

# 3. 评估要点

## 3.1 验收标准

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| P0 | 存储 + 注入 + 设置页增删改查 + 单一上限 | 新建条目后，新开一个会话能看到它；删除后消失；重启后状态不变；超限时不发起请求且给出可执行的调整提示 |
| P1 | 启停 + 导入导出 + `/memory` 命令 | 导出的文件可重新导入并得到等价状态；超限时 `/memory list`、`/memory drop` 仍可执行 |
| P2 | 与台账冲突的并列呈现 | 台账与全局记忆含冲突内容时，模型可见两段独立文本 |

## 3.2 关键决策记录

以下三项在评审时已确认，实现按「采用」列执行；备选方案保留，以便将来回退时有据可查。

### 3.2.1 存储用领域存储还是插件自管文件

- 倾向：**领域存储**。校验、原子性、版本迁移都是现成的，自管 JSON 要重新实现一遍还更容易出错。
- 代价：内容不在一个显眼的独立文件里，用户想直接用文本编辑器改需要先找到 `storages` 目录。
- 若要求「一眼可见、可直接手改」：改为自管单个 Markdown 文件，牺牲校验与原子性。

### 3.2.2 是否允许模型写入全局记忆

- 倾向：**默认关闭**，只在用户显式开启后允许「建议并等待确认」。
- 理由：全局作用域下模型误判的代价是全体会话，与台账那种「会话内可随时纠正」的性质不同。
- 若希望更顺手：开启后仍需用户在卡片上点确认，不直接落盘。

### 3.2.3 是否对子 agent 生效

- 倾向：**生效**。子 agent 同样代表用户工作，若全局偏好对它失效，会出现「主对话用中文、子 agent 用英文」的割裂。
- 代价：子 agent 的上下文更长，预算压力更大。
- 若要求隔离：通过配置按 scope 关闭，但默认应打开。

## 3.3 已确定的默认值

三项决策按以下实现，不再逐轮确认：

| 决策 | 采用 | 理由摘要 |
| --- | --- | --- |
| 存储方式 | 领域存储（`storageDomain`） | 校验、原子写入、版本迁移现成；自管 JSON 要重写一遍且更易出错 |
| 模型写入 | 默认关闭（`allowAgentWrite: false`） | 全局作用域下误判污染所有会话，用户无法事先审查 |
| 子 agent | 生效 | 否则主对话与子 agent 的语言/工具偏好会割裂 |

容量上限为单一硬上限，见 2.5.2 与 2.9：注入预算 400 token，超出则不回答并提示用户调整。

## 3.4 与既有插件的实现复用

可以复用的部分，避免重复造轮子：

- **注入形态与字节稳定渲染**：直接沿用要求台账 `lib/render.js` 的做法。
- **HTTP 路由 + 信任栅栏 + JSON 响应**：沿用要求台账 `lib/route.js` 的结构。
- **设置页 UI**：沿用 `settings.section` 注册方式，样式用宿主主题 token。

不需要复用的部分：投影机制。全局记忆没有所属会话，`sessionProjections` 在这里不适用，见 1.1。
